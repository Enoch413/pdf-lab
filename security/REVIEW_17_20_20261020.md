## 17. 서버 인가

운영 Firestore ruleset `e5842767-759f-42ec-ad63-253db55443bd`(2026-10-07), Storage ruleset `c9fc1c15-5196-43cb-a871-8f334ca8df31`(2026-07-22)을 보존했다. 전체 release 이름·조회 파일은 사본의 manifest.json에 있다. 인증 토큰과 운영 문서는 보존하지 않았다.

확인된 P1 문제와 최소 수정:

- `users` 자기 생성에 role 제한이 없어 `admin` 자가 등록이 가능했다. 자기 생성은 권한 없는 student로 제한하고 UID 위조·자기 반/문법 권한 부여를 거부한다. 다른 계정 생성·권한 변경은 기존 `adminScope: all` 관리자만 허용한다.
- 자기 수정의 `changedKeys()`는 새 필드 추가를 포함하지 않았다. `affectedKeys()`로 바꾸고 기존 비밀번호 초기화 플래그 변경은 유지한다.
- 제한 강사도 users 전체를 읽을 수 있었다. 본인/담당 반 조회만 허용하고 앱도 최대 30개 반씩 `array-contains-any` 쿼리한다. 전체 관리자는 기존 전체 조회를 유지한다. 문서에 든 uid보다 실제 Auth/문서 ID를 우선한다.
- 오답 7개 컬렉션은 모든 관리자가 다른 소유자 데이터에 접근할 수 있었다. 읽기·생성·수정·삭제에 ownerUid를 강제한다. 신규 문서를 읽은 뒤 생성하는 기존 transaction과 삭제 표시 저장을 허용한다.
- `questionIssues` 수정 시 기존 소유자를 확인하지 않아 본인 userId로 바꾸는 탈취가 가능했다. 기존·신규 소유자를 모두 검사한다.

Storage는 기존 PDF LAB 관리자 전용 공유 라이브러리 정책을 유지했다. 이 공유 자료는 관리자 간 공동 사용 대상이며 개인 오답과 구별된다. 학생·비로그인의 공유 이미지 읽기/쓰기는 거부됨을 확인했다.

## 18. 의존성

`dependencies.json`에 로컬 JS 11파일 SHA-256, 버전/공식 upstream 참고 링크, Firebase compat 10.12.2 CDN 4파일의 SHA-256/SHA-384, 설치된 Python 버전과 필수 의존성을 기록했다. 로컬 해시는 현재 파일의 변경 감지 기준이며 upstream 원본과의 일치 인증은 아니다. Firebase script는 기록한 SRI와 crossorigin을 두 화면에 적용했다.

Supply Chain Risk Auditor collector로 원 프로젝트의 Python 4개를 재검사했다. 고정 버전인 Pillow만 실제 핀으로 검사됐고 나머지 3개는 latest fallback이다. 별도로 작업 폴더 밖에 현재 사용 버전만 적은 임시 manifest를 만들어 **PyPI 1개·npm 5개를 정확한 버전으로 검사**했다. 라이브러리를 설치하거나 업그레이드하지 않았다.

- 정확 버전 검사: jsPDF 2.5.2에 **12개 advisory**. 나머지 Firebase 10.12.2, html2canvas 1.4.1, JSZip 3.10.1, PDF.js 4.10.38, Pillow 13.0.0은 collector가 검사한 advisory에서 발견 없음.
- collector는 html2canvas의 Maintenance activity·Publisher concentration, jsPDF의 Publisher concentration도 표시했다. 이는 호출 경로에서 재현한 취약점과 구별한다.
- JSON용 `requirements-core.txt`의 Pillow 13.0.0과 현재 NumPy 2.5.4는 설치 메타데이터에 필수 전이 의존성이 없다. `pip check` 통과. OCR의 pytesseract/opencv-python은 미설치이며 기존 선택 requirements는 그대로 유지했다.
- npm lockfile이 없으므로 vendor 내부에 묶인 전이 버전 전체를 검사했다고 해석하면 안 된다. OCR requirements의 미설치/미고정 항목도 검증 완료가 아니다.

## 19·20. 공통화·대량 저장·탐색

정답 편집 파서를 `app/answer_editor.js`에 모으고 기존 화면별 OCR fallback 차이를 유지했다. 호출이 사라진 block wrapper 3개만 제거했다. UI/DB 전체를 재작성하거나 일반 화면의 큰 잔존 코드 묶음을 추정으로 삭제하지 않았다.

`app/firebase_helpers.js`의 batch는 450문서/직렬화 UTF-8 4MiB 제한을 적용하고 900KiB 초과 단일 문서를 첫 쓰기 전에 거부한다. Firestore index 확장 크기는 서버에서 최종 판정한다. 공용 문항 등록·메타데이터 수정·오래된 문항 삭제가 같은 helper를 쓴다. 모의 DB에서 2,307문항을 6번의 commit 요청으로 저장했다. 문서 쓰기 수·과금이 줄었다는 뜻은 아니다. 실패하면 source manifest 갱신·이전 문항/이미지 정리를 진행하지 않는다. 이미 성공한 이전 batch는 남으므로 전체 출처가 하나의 원자적 transaction인 것은 아니다. 재시도는 같은 문서 ID를 upsert한다. 이미지 업로드와 실제 네트워크 지연 시간은 측정하지 않았다.

시작 화면·반별·파이널·일반 상단에 쏠북메이커를 연결했다. draft 문구를 문제 초안으로 정리하고 반별 작업 순서와 온라인 CHECK 안내를 추가했다. 기존 레이아웃·색·글꼴·스키마 키를 유지했다. 기존 글꼴·로고·vendor 바이트는 변경하지 않았다.

실브라우저에서 시작→메이커→반별→파이널→일반 이동을 확인했다. 두 Firebase 화면의 SRI 로딩 후 로그인 안내가 정상 표시되고 각 화면 console warn/error는 없었다. 새 모듈과 링크의 EXE 패키징 목록도 공개 검사에 포함한다. 실계정 로그인이 필요한 업무 흐름은 이번에 실행하지 않았다.
